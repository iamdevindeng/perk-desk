# Perk Desk: Architecture

Source of truth for file locations, names, data shapes, endpoints and agent behaviour. Product context: `docs/PRD.md`. Qloo details: `docs/QLOO_API.md`.

## 1. Overview and data flow

```
Browser (single page, useState only, profile in localStorage)
  │  1. POST /api/plan  {profile, brandNames, preferences}        → JSON PlanResponse
  │       ① resolveBrands (Qloo /search)  ② pickCategories (Qloo /v2/tags + DeepSeek) + guards 1–2
  │  2. user edits/confirms categories (guard 3); edits saved as preferences (guard 4)
  │  3. POST /api/run   {branches, brands, categories, exclusions} → NDJSON stream of TraceEvent
  │       ③ findMerchants (Qloo /v2/insights, seeded + baseline per branch × category)
  │       ④ filter + score (deterministic)   ⑤ data check (DeepSeek, ≤1 adjacent retry per category)
  │       ⑥ shortlist (code) + pitches (DeepSeek selects facts, code renders)   → final `result` event
  └─ renders trace, evidence cards, Leaflet map, CSV export, follow-up status
Server (Next.js route handlers, Node runtime)
  src/lib/qloo  → cache (Upstash or in-memory) → https://hackathon.api.qloo.com
  src/lib/agent → AI SDK 7 + @ai-sdk/deepseek ("deepseek-flash", thinking disabled, temperature 0)
  src/lib/fallback → used when DeepSeek is missing/fails: same output shapes, mode "fallback"
```

**Why two endpoints:** the user must confirm categories before any merchant search. Instead of pausing and resuming one agent run, `/api/plan` ends after step ②, and `/api/run` starts at step ③ with the confirmed categories. Both endpoints are stateless; the client sends everything the server needs.

## 4. Endpoints

Branch lookup (`POST /api/branches`) resolves its center from an exact preset city label, then the normalized bundled city table (`findUsCityCenter`), then Qloo `resolveLocality`; the chosen center supplies `cityLabel` and the place-search coordinates.

### 4.1 `POST /api/plan`
- Body: `PlanRequest` (if `presetId` is set, the server **ignores the body's profile fields and brands** and loads them from `src/data/presets/<presetId>.json`; `preferences` from the body are still used).
- Flow: validate (400 JSON `{ error: "bad_request", issues }`) → cache lookup `plan:<hash>` (hit → serve without counting) → production shared-store gate and limit check (§7) → resolve locations (§5.1) → plan agent (§5) or fallback plan (§8) → cache store → 200 JSON `PlanResponse`.
- In Vercel production, missing shared-store configuration or a rate-limit service failure/timeout → HTTP 503 JSON with a clear message (§7), before live Qloo or DeepSeek calls.
- Missing `QLOO_API_KEY` → HTTP 503 JSON `{ error: "config", message }`. Qloo `auth` → 502 `{ error: "auth", message }`; Qloo `quota` → 503 `{ error: "quota", message }`; other Qloo failures → 502 `{ error: "upstream", message }` (messages from §11). The client shows `message`. All brands unresolved → 200 with `unresolved` filled, `categories: []`, warning "None of these brands were found on Qloo".
- `export const maxDuration = 300;` No `runtime` export.

### 4.2 `POST /api/run`
- Body: `RunRequest`. Validation errors → 400 JSON (not a stream). In Vercel production, missing shared-store configuration or a rate-limit service failure/timeout → HTTP 503 JSON before live streaming. Otherwise → **200** `Content-Type: application/x-ndjson; charset=utf-8`, `Cache-Control: no-store`, a stream of `TraceEvent`. The stream **always ends with `done`**; exactly one `result` or one `error` before it (or one `limited`).
- Flow: validate → cache lookup `run:<hash>` (hit → replay stored events with `RUN_REPLAY_DELAY_MS` between them, then `done`, without counting) → production shared-store gate and limit check (§7; over budget → `limited` + `done`) → run agent (§6) or fallback run (§8) → `result` → store `{events}` in cache → `done`.
- `export const maxDuration = 300;`
- `src/lib/stream.ts`: `createNdjsonResponse(work: (emit: Emit) => Promise<void>): Response` where `type Emit = (event: TraceEvent) => void`. It catches any thrown error, emits `error` (code `internal` unless typed) and always emits `done`, then closes.

### 4.3 Client (`src/lib/run-client.ts`)
`postPlan(request): Promise<PlanResponse>` and `streamRun(request, onEvent): Promise<void>` (fetch → `res.body.getReader()` → `TextDecoder` → buffer → split on `\n` → `JSON.parse` → `TraceEventSchema.safeParse`; skip invalid lines with `console.warn`).

## 5. Plan agent (`src/lib/agent/plan-agent.ts`) — steps ① ②

### 5.1 Location resolution (code, before the agent)
For each branch without `lat/lon`: Qloo locality lookup of `branch.address` (QLOO_API.md §5) → set coords, `locationSource: "qloo_locality"`, add warning "Branch X location is approximate; pick it on the map to refine". City center: from `src/data/presets/cities.json` if the label matches, then the normalized bundled city table (`findUsCityCenter`), else Qloo locality lookup of `city`; the response keeps the request's city label. Branch still unresolved → drop it with a warning; if no branch remains → 200 with warning and empty categories.

### 5.2 Loop
```ts
const result = await generateText({
  model: agentModel(),                       // src/lib/agent/model.ts
  instructions: PLAN_SYSTEM_PROMPT,          // src/lib/agent/prompts.ts
  prompt: buildPlanUserPrompt(context),      // brand names, city, branch count, preferences
  tools: { resolveBrands, searchCategories, submitPlan },
  toolChoice: "auto",
  stopWhen: [isStepCount(PLAN_MAX_STEPS), () => context.plan !== null],
  temperature: 0, maxRetries: 1,
  abortSignal: AbortSignal.timeout(PLAN_TIMEOUT_MS),
  providerOptions: { deepseek: { thinking: { type: "disabled" } } },
  onStepFinish: (step) => { /* trace agent_note with step.text truncated to 200 chars */ },
});
```
`PlanContext` (`src/lib/agent/context.ts`): request, emit, `brandsByInput: Map<inputName, BrandResolution>`, `brandTags: Map<entityId, TagRef[]>` (allowed tags only), `candidateCategories: Map<tagId, label>`, `submitCount`, `plan: PlannedCategory[] | null`, `qlooCalls`.

### 5.3 Tools (in `src/lib/agent/tools/`; each exports `buildXTool(context)` returning an AI SDK `tool(...)` plus a plain function used by fallback)
- **resolveBrands** `{ names: string[] (1..10) }` → for each name: Qloo `/search` (types=brand, take=3). Matching (code): normalize with `normalizeName` from `merchants/name-match.ts` (§6.2 item 6); `exact` if equal; `prefix` if one normalized name starts with the other at a word boundary (e.g. "ulta beauty" ↔ "ulta", "sierra nevada" ↔ "sierra nevada brewing"; but "rei" ↔ "reiss" is NOT a prefix match). Check candidates in Qloo order: first exact wins, else first prefix; else `ambiguous` (e.g. "REI" → "Recreational Equipment Inc", "Real Madrid CF", "Reiss"). If `request.brandOverrides[inputName]` is one of the candidates, it wins (`matchKind: "user"`). Zero results → unresolved. Stores **allowed** tags for every candidate (§5.5). Returns to the model: per name `{ inputName, status: "resolved"|"ambiguous"|"unresolved", chosen?, candidates: [{ entityId, name, popularity, shortDescription, tags: [names of up to 25 allowed tags] }] }`.
- **searchCategories** `{ query: string }` → Qloo `/v2/tags` (`filter.query`, `filter.tag.types=urn:tag:category:place`, take=`TAG_SEARCH_TAKE`) → drop blacklisted slugs (guard 1) → add to `candidateCategories` → return `[{ tagId, label, knownIndependents? }]` (density from cache `density:<citySlug>:<tagId>` if present; `usableInDemoCities: true` if in `category-defaults.json`).
- **submitPlan** `{ brandChoices: [{ inputName, entityId }], categories: [{ tagId, evidence: [{ brandEntityId, brandTagId, reason }] }] }` → runs guards (§5.4). Returns `{ accepted: boolean, kept: tagId[], errors: string[] }`. If `kept.length >= PLAN_MIN_CATEGORIES` → `context.plan` is set (loop stops). Else errors go back to the model for **one** correction (second submit is final whatever the result).

### 5.4 Guards (`src/lib/agent/guards.ts`, pure functions, each unit-tested)
- **Layer 1 `checkCategoryCandidate(tagId, candidates, blacklist)`**: tag matches `CategoryTagIdSchema`, is in `candidateCategories` (returned by `searchCategories` in this run), and its slug contains no `categorySlugKeywords` entry.
- **Layer 2 `checkEvidence(evidence, brandTags)`**: `brandEntityId` is a chosen brand of this plan; `brandTagId` is in `brandTags.get(brandEntityId)` (allowed tags only); `reason` non-empty. A category keeps only valid evidence items; a category with zero valid items is dropped.
- Brand choices: an ambiguous brand's `entityId` must be one of its candidates; otherwise use candidate[0] (`matchKind: "fallback"`). Resolved brands keep the code's choice even if the model says otherwise.
- Dedupe categories; cap at `PLAN_MAX_CATEGORIES` (keep order given by the model).
- Every dropped item emits a `guard` trace event (`layer`, short reason).
- After the loop: if fewer than `PLAN_MIN_CATEGORIES` categories survive (or the loop failed), complete with `fallback-plan.ts` categories (source `"fallback"`, evidence from rules) and add a warning.

### 5.5 Allowed brand tags (compliance + prompt size)
Keep a brand tag only if its `type` is **not** in `category-blacklist.json → brandTagTypeDenylist` (this removes target age/gender/income, customer segments, competitors, etc.). Also drop any tag whose type has a `:`/`_`-separated segment equal to `age`, `gender`, `income` or `demographic` (defensive; QLOO_API §2). Then keep at most `BRAND_TAGS_MAX` (40) per brand, preferring types in this order: `urn:tag:genre:brand`, `urn:tag:keyword:qloo`, `urn:tag:lifestyle:qloo`, `urn:tag:interest_adjacency:qloo`, `urn:tag:product_category:qloo`, `urn:tag:product_service:qloo`, `urn:tag:industry:qloo`, `urn:tag:consumption_context:qloo`, `urn:tag:wikipedia_category`, then anything else. Tag-type coverage varies by brand; handle missing types.

### 5.6 Prompt outline (`PLAN_SYSTEM_PROMPT`)
```
You are Perk Desk's planning agent for a community credit union's local-merchant perks program.
Goal: pick 2-6 Qloo place categories of LOCAL merchants that members with these brand tastes would love, then call submitPlan once.
Steps: 1) call resolveBrands with all brand names. 2) For ambiguous brands choose the candidate that fits a consumer
spending context (e.g. "REI" = Recreational Equipment Inc, not a football club). 3) Call searchCategories with 3-8 short
merchant keywords derived from the brands' tags (e.g. "yoga", "bicycle", "coffee", "brewery"); call several in one step.
4) Call submitPlan. Every category needs evidence: brandEntityId + an exact brandTagId from that brand's tags + a short reason.
Rules: only use tagIds returned by searchCategories. Prefer categories whose merchants could offer a member discount
(shops, cafes, restaurants, studios, salons). Prefer categories marked usableInDemoCities or with knownIndependents >= 6.
Respect institution preferences: avoid categories the institution removed before unless evidence is strong; consider ones it added.
Never use or mention age, gender, income or ZIP. Do not invent IDs. Be brief.
```
User prompt: brand names, city, branch count, preferences (removed/added labels). Cached densities arrive through `knownIndependents` in `searchCategories` tool results.

## 6. Run agent (`src/lib/agent/run-agent.ts`) — steps ③–⑥

`RunContext`: request, emit, `results: Map<tagId, CategoryOutcome>` (per category: merged `MerchantCandidate[]`, independent count), `replacements: Map<originalTagId, newTagId>`, `candidateCategories` (seeded with confirmed categories + their `adjacent` lists from `category-defaults.json`), `finished`, `qlooCalls`, excluded counters.

### 6.1 Loop (③ ⑤)
Same `generateText` shape as §5.2 with `RUN_SYSTEM_PROMPT`, tools `{ findMerchants, searchCategories, finishResearch }`, `stopWhen: [isStepCount(RUN_MAX_STEPS), () => context.finished]`, `abortSignal: AbortSignal.timeout(RUN_AGENT_TIMEOUT_MS)`.
- **findMerchants** `{ tagId, replacesTagId? }` → for every branch: two Qloo insights calls (QLOO_API.md §4): seeded (`signal.interests.entities` = all brand IDs, `feature.explainability=true`) and baseline (no signal), both with `filter.location=POINT(lon lat)`, `filter.location.radius`, `filter.tags=<tagId>`, `take=INSIGHTS_TAKE`. Then step ④ (§6.2) → stores outcome → writes density cache `density:<citySlug>:<tagId>` = independent count → returns `{ tagId, label, independentCount, thin: independentCount < MIN_INDEPENDENTS, sampleNames: first 3 }`.
  - Guard: `replacesTagId` allowed only once per original tag (`replacements`), the new tag must pass layer 1 against `candidateCategories`, and the original must have been thin. Violations return an error string, no Qloo calls.
- **searchCategories**: same tool as plan (§5.3), adds to `candidateCategories`.
- **finishResearch** `{ note: string }` → `context.finished = true`.
- Prompt outline (`RUN_SYSTEM_PROMPT`): "Call findMerchants for every confirmed category (all in one step). For each result with thin=true, you may try ONE adjacent category (from the provided adjacent list or searchCategories) via findMerchants with replacesTagId; if still thin, accept it. Then call finishResearch. Do not write pitches."
- **Deterministic completion:** after the loop (or if it throws), call `findMerchants` directly for any confirmed category with no outcome. So the result never depends on the model calling every tool.

### 6.2 Filter and score (④, `src/lib/merchants/*`, pure functions)
For one category: merge seeded and baseline lists per branch into `MerchantCandidate { place, branchId, distanceMeters, seededRank|null, baselineRank|null, affinity|null, explain }`, then:
1. `filter.ts`: drop `isClosed`; drop if `primaryGenreId` last part (after `urn:tag:genre:place:`) is in `noisePrimaryGenres`; drop `excludeEntityIds`; drop if `nameMatches(place.name, signedNames)`. Count each reason.
2. `chains.ts`: `isNationalChain(name)` (word-boundary match against `national-chains.json`) → **drop** (counted as `nationalChain`). `markDuplicates(allCandidates)`: ≥ 2 distinct entityIds with the same normalized name across the whole run → `multiLocation = true`.
3. `distance.ts`: haversine meters from the branch; drop if > branch radius × 1.1 (Qloo radius is approximate).
4. A place found for several branches keeps the **nearest** branch. A place found in several categories keeps the category with the higher score.
5. `scoring.ts`:
   - `rankLift = baselineRankOrMissing - seededRank` where `baselineRankOrMissing = baselineRank ?? baselineLength + 1`; `null` if not in the seeded list.
   - `affinityNorm`: min-max of `affinity` within the same branch×category seeded list (all equal → 1); 0 if absent.
   - `liftNorm = clamp((rankLift + 10) / 20, 0, 1)`, 0 if null. `distanceNorm = 1 - min(distance / radius, 1)`. `ratingNorm = businessRating/5 ?? tripadvisorRating/5 ?? 0.5`.
   - `score = 0.40*affinityNorm + 0.25*liftNorm + 0.20*distanceNorm + 0.15*ratingNorm` (weights in `config.ts`), rounded to 3 decimals.
   - `tasteSignal = seededRank !== null`. Sort: `tasteSignal` first, then `score` desc, then name.
   - `brandShares`: from `explain` scores mapped to brand names, as integer percentages (largest-remainder so they sum to 100); empty if no explain.
6. `name-match.ts`: `normalizeName` (NFKC, lowercase, `&`→`and`, strip punctuation, drop leading `the`, drop trailing `llc|inc|co|company`, collapse spaces); `nameMatches(a, list)` = equal normalized, or one contains the other when the shorter is ≥ 5 chars. Business members (optional extra X2 only; until then always `false`): `businessMember = nameMatches(place.name, businessMemberNames)`.
7. **Independent count** for ⑤ = distinct entityIds in the category after filtering with `multiLocation === false`.

### 6.3 Shortlist and pitch (⑥)
- `shortlist.ts`: `SHORTLIST_TOTAL` (10). Quota per branch = `ceil(10 / branches)`. Within a branch, round-robin across categories (best first). If a branch runs short, fill from the remaining best overall. Then trim to 10.
- **Brand check** (chains, 3rd rule): for each shortlisted merchant (max `BRAND_CHECK_MAX`), Qloo `/search` types=brand take=1 with the merchant name; if normalized names are equal and `popularity >= BRAND_CHECK_MIN_POPULARITY` (0.5) → `multiLocation = true` (badge only, still listed). Cached like all Qloo calls.
- `pitch-writer.ts`: one `generateText` call for all shortlisted merchants (temperature 0, thinking disabled, existing timeout/cancellation) with `Output.object` and strict JSON `{ pitches: [{ entityId, fact }] }`. Each `fact` is `category`, `taste`, `distance`, or `rating`. The prompt contains only institution name, merchant IDs/names, and code-built available fact sentences; descriptions and selling points are excluded. No model-provided prose or numeric values are accepted. Unknown IDs, duplicate selections, unavailable facts, and overlong rendered pitches fall back per card; provider/schema failures use templates for the batch and keep the existing fallback mode/cache behavior.
- **Pitch grammar** (`pitch-template.ts`, checked by `guards.ts → checkPitch(pitch, card, institutionName)`): accept only exact code-rendered candidates for the current card/institution, or the short template, within 600 characters. Fact pitches have three code-owned sentences: introduction, one verified fact, and a tentative 10-minute call invitation. The short template omits optional facts. Category requires non-empty category/branch labels; taste requires `tasteSignal` and positive brand shares; distance must be finite and non-negative; ratings must be finite and in the existing rating range, with business/Tripadvisor source named explicitly. All labels are quoted and control characters escaped, so label punctuation cannot become model assertions. Numeric claims occur only in their corresponding fact or the call length; there is no natural-language denylist or global name masking. The template tries available facts in deterministic order, then a short version; an identity too long even for that keeps the merchant with an empty pitch. `pitchSource: "agent"` means the model selected a valid fact; all fallback choices use `"template"`.
- Cached run results are checked against this grammar before replay. Legacy free-text pitches are replaced using the cached card facts and current request institution name; impossible overlong identities get an empty pitch. This does not invoke research, consume rate limits, rewrite cached values, or change cache keys/TTLs/response shapes.
- `googleMapsUrl = https://www.google.com/maps/search/?api=1&query=<encodeURIComponent(name + " " + address)>` plus `&query_place_id=<googlePlaceId>` when present.
- Emit `step` events for each of the six steps (`start`/`done` with counts), then `result`.

## 7. Cache, rate limits, presets (`src/lib/store/*`)

**Cache** (`cache.ts`): `getJson(key): Promise<unknown | null>`, `setJson(key, value, ttlSeconds): Promise<void>`. If `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are set → `@upstash/redis` (`new Redis({ url, token })`); else an in-memory `Map<string, { value, expiresAt }>` (module-level; fine for local dev; note in README that serverless instances don't share it). Callers parse values with zod; a parse failure counts as a miss. Keys (all prefixed `pd:v1:`):

| Key | Value | TTL |
|---|---|---|
| `qloo:<sha256(path + canonical params)>` | slim Qloo result (never raw JSON) | 7 days |
| `density:<citySlug>:<tagId>` | independent count (number) | 30 days |
| `plan:<sha256(canonical PlanRequest)>` | `PlanResponse` | 30 days |
| `run:<sha256(canonical RunRequest)>` | `{ events: TraceEvent[] }` (incl. `result`) | 30 days |

`citySlug` = lowercase city with non-alphanumerics → `-`. Canonical JSON = keys sorted recursively (`hash.ts`).

**Rate limit** (`rate-limit.ts`): `checkLimit(scope, ip): Promise<{ ok: boolean; reason?: "ip" | "global" | "store"; message?: string }>` checks both the per-IP and global budgets. A `store` denial includes a safe message for the HTTP 503 response. Upstash: `@upstash/ratelimit` `Ratelimit.fixedWindow(limit, "1 d")`, prefixes `pd:v1:rl:<scope>:ip` and `pd:v1:rl:<scope>:global` (identifier `"all"`). In-memory: `Map<key, { count, windowStart }>` with a 24 h fixed window. Limits from `config.ts`: plan 30/IP/day + 300 global/day; run 10/IP/day + 150 global/day.
- Order in routes: cache hit → served, **never counted**. On every cache miss, enforce the production shared-store gate below, then check both the per-IP and global limits. Preset requests use the same limits when they need live research.
- Production gate: `getEnv()` in `src/lib/env.ts` reads `VERCEL_ENV`; `isVercelProduction()` returns whether it equals `"production"`. In that environment, both `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are required for every cache miss, including cold-preset requests. Missing either → HTTP 503 with "Live research is disabled: shared rate-limit store not configured." A rate-limit service failure or timeout returns HTTP 503 with "Live research is disabled: shared rate-limit store unavailable." Production never falls back to in-memory limits. Cache hits still work when the cached value can be read. Local development and preview deployments retain in-memory fallback and its warning.
- Over limit: plan → 200 JSON `{ limited: true, message, ... empty arrays }`; run → `limited` event + `done`. Message: "Today's live-research limit has been reached. The Denver and Austin demos still work instantly."

**Presets:** `src/data/presets/*.json` hold only hand-written inputs (fictional institution, branches with coords, lists, brand names). The first run computes results live and caches them under `plan:`/`run:` keys; later runs replay from cache. No preset results are committed.

**Usage visibility** (`usage.ts`): `withRunUsage<T>(ip, work, scope = "run")` uses Node's `AsyncLocalStorage` to isolate concurrent request counters and emits one structured server log line when live research finishes or fails: `[usage] scope=plan|run ip_hash=<short sha256> qloo_calls=<n> llm_calls=<n>`. `recordUsageCall("qloo" | "llm")` counts each outbound HTTP attempt, including retries and failed attempts; cache hits add zero. The IP is represented only by the first `USAGE_IP_HASH_LENGTH` (12) SHA-256 hex characters; no raw IP or secret values are logged. Cached replays do not emit a live usage line. Devin can inspect the counts in Vercel logs. The same context enforces `PLAN_QLOO_CALL_CAP = 70` and `RUN_QLOO_CALL_CAP = 120`; the Qloo client checks it before fetching and throws a non-retryable `budget` error when the cap is reached. A limited run uses gathered candidates, emits "Stopped early to stay within the research budget", and is not cached.

## 8. Fallback (`src/lib/fallback/*`)

Triggered when: no `DEEPSEEK_API_KEY`, `PD_AGENT_DISABLED=1`, `APICallError`, timeout/abort, the loop ends without a valid plan, or any unexpected agent exception. Not triggered by Qloo `auth`/`quota` errors (those end the request with an error). A `fallback` trace event states the reason; `mode: "fallback"`.
- **fallback-plan.ts**: resolve brands in code (exact/prefix; ambiguous → highest-popularity candidate; `matchKind: "fallback"`). Categories from `category-map.ts`: ordered keyword rules over each brand's **allowed** tag names/ids, e.g. `coffee|espresso → coffee_shop, cafe`; `tea → tea_house`; `bakery|pastry|donut → bakery, donut_shop`; `dessert|ice cream|candy|chocolate → dessert_shop, ice_cream_shop`; `beer|brew|craft beer → brewery, beer_garden`; `wine → wine_bar, wine_store`; `cocktail|spirits|liqueur|aperitif → cocktail_bar`; `pet|dog|cats|kitten → pet_supply_store, pet_groomer`; `yoga|fitness|athletic|gym|training|running → gym, sporting_goods_store`; `outdoor|camping|hiking|cycling|bicycle → sporting_goods_store, bicycle_shop`; `beauty|cosmetic|skincare|makeup → nail_salon, day_spa`; `hair → hair_salon, barber_shop`; `book → book_store`; `music|vinyl|record → record_store`; `fashion|apparel|clothing|boots|western → clothing_store, womens_clothing_store, mens_clothing_store`; `jewelry → jewelry_store`; `gift → gift_shop`; `salad|healthy|plant-based|organic → health_food_restaurant, juice_shop`; `burger → hamburger_restaurant`; `mexican|burrito|taco → mexican_restaurant, taco_restaurant`; `pizza → pizza_restaurant`; `grocery|natural foods → health_food_restaurant, cafe`; `spa|massage|wellness → day_spa, massage_spa`. Every target is `urn:tag:category:place:<slug>` and **must exist in `category-defaults.json`** (unit test asserts this). Rules live in `category-map.ts` as a plain array `{ keywords: string[], categories: string[] }[]`; keywords match case-insensitively at the start of a word in the tag **name** (regex `\b<keyword>`, keyword regex-escaped), never against the tag id (ids contain words like `category`). Each produced category gets evidence `{ brand, brandTag = the matching tag, reason: "Rule: tag contains '<keyword>'" }` so layer 2 still holds. Take the 4 most frequent categories (ties → order of rules). If none match: union of the brands' quick-segment defaults, else `coffee_shop, brunch_restaurant, brewery, gift_shop`.
- **fallback-run.ts**: `findMerchants` for every confirmed category; for thin ones, try the first `adjacent` tag from `category-defaults.json` once; shortlist; template pitches for all.
- **pitch-template.ts** (3 sentences, only card fields): `"Hi {name} team, {institution} is building a local perks program for members near our {branch} branch." + " Qloo taste data links our members' favorite brands ({top brands}) to {category label} spots like yours{rating clause}." + " Would you be open to a 10-minute call about featuring a member offer?"` where `{rating clause}` = `", and your {businessRating}-star rating stands out"` only when present.
- Fallback must still be Qloo-driven (brand search, tags, places); only the LLM is replaced.

## 11. Errors

`src/lib/qloo/client.ts` throws a `QlooError`: a plain `Error` with extra fields, built by `createQlooError(code, status, message)` and recognized by `isQlooError(value): value is QlooError` (type `QlooError = Error & { code: QlooErrorCode; status: number | null }`; no class). Codes (`"config" | "auth" | "quota" | "timeout" | "upstream" | "network" | "bad_request"`). Mapping: 401/403 → `auth`; 429 with `x-month-ratelimit-remaining: 0` → `quota` (no retry); other 429 → retry once after 1 s, then `upstream`; 5xx → `upstream`; abort → `timeout`; fetch failure → `network`; 400 → `bad_request`. Routes map these to `ErrorCode` + a user message:

| Code | User message |
|---|---|
| `config` | "Server is missing its Qloo key." |
| `auth` | "Qloo refused our key. Demo presets may still work from cache." |
| `quota` | "Live research is paused (Qloo quota). Demo presets may still work from cache." |
| `upstream` / `timeout` / `network` → `upstream` | "Qloo is having trouble; try again in a minute." |
| `no_brands` | "None of these brands were found on Qloo." |
| `internal` | "Something went wrong." (details only in server log, never keys) |

Qloo `config` → `config`; Qloo `bad_request` → `upstream` (it means our code built a bad query; log it).

A single failed Qloo call inside `findMerchants` (one branch) is **not fatal**: record a warning, continue with the other calls.
